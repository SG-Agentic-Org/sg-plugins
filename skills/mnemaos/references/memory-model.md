# Memory model — the model-agnostic core

This is the part of MnemaOS that is the same for everyone. Read it in Phase 2 before
designing the user's system. It defines: the one memory layer, the types of memory inside
it, and the decision tree for "where does this piece of information go".

## One layer: the vault is the truth

MnemaOS has **one layer of memory**: a folder of Markdown files — the vault. The vault
is the single source of truth. There is no separate database, no vector index, no cloud
mirror. Retrieval is "read the index, open the file", not embeddings.

Why one layer: a richer system (a retrieval cache, a mobile projection, cross-device sync)
solves problems a person only has once their vault is large and used across devices. On day
one those layers are pure overhead — infrastructure to set up, maintain, and debug. MnemaOS
ships only the layer that earns its keep immediately; a retrieval cache, a mobile projection,
and cross-device sync are out of scope for this package (see the boundaries in the package
README). The vault must work fully on its own.

## How the agent reads memory (retrieval without RAG)

1. **Startup.** At the beginning of a session the agent reads `_start-here.md` — a compact
   map of "who the user is, active projects, key people, where to write what". It does
   **not** load the whole vault. This keeps the context small and avoids anchoring the
   agent on stale detail.
2. **On demand.** When a task needs detail, the agent reads the specific file — a project
   README, a person card, a decision. `_index.md` lists what exists and where.
3. That is the whole retrieval story. It is transparent (the agent reads files you
   can also read) and needs zero infrastructure.

## Types of memory inside the vault

Each file exists for a reason. The type tells the agent when to write there.

| Type | Where | When to write |
|------|-------|---------------|
| **Profile** (static facts about the person) | `profile.md` | Rarely; manual or semi-manual edits |
| **Decision** (an architecture/policy choice) | `decisions.md` (append) | A meaningful choice was made |
| **Lesson** (a rule for the future) | `lessons.md` (kept within a size budget) | A repeating mistake or anti-pattern was caught |
| **Entity** (a person / project / concept) | `people/`, `projects/`, `cards/` | A durable entity appeared or changed → distillation/closure |
| **Episode** (a fresh fact from one session) | `inbox.md` (volatile) | A single fact on a topic, not yet a pattern |
| **Note** (`type: note`, catch-all) | `inbox.md` or `cards/` | Default; anything not person/project/concept/decision |

The vault skeleton (in `assets/vault-template/`):

```
<chosen folder>/
  README.md       — what this memory is and how to use it (for the human)
  _start-here.md  — THE AGENT'S ENTRY POINT: who, active projects, rules, links
  profile.md      — who the user is: static facts, context, preferences, working style
  projects/       — one file/folder per project (README + working files)
  people/         — cards for people (colleagues, clients, partners)
  cards/          — cards for concepts / decisions-as-entities (distillation files here)
  decisions.md    — log of important decisions (append, dated)
  lessons.md      — "do not do this again" rules (budgeted so it does not sprawl)
  inbox.md        — buffer of fresh episodes (volatile; tended by hygiene/closure)
  _index.md       — auto-index of the vault (generated by scripts/index_vault.py)
```

Principles of the skeleton:

- **Cards vs working files.** A *card* is a `.md` file **directly** inside `people/`,
  `cards/`, `Wiki/`, or a project's card file `projects/<slug>.md`. It carries the
  frontmatter contract and is indexed. A *working file* is anything nested deeper — e.g.
  `projects/<slug>/files/brief.md`, a spreadsheet, a raw doc. Working files are NOT cards:
  they need no frontmatter and are not validated by the indexer or smoke test. This is what
  lets a project hold arbitrary real files (briefs, reports, data) without forcing frontmatter
  on every one — important when adopting an existing folder.
- **`_start-here.md` is the one required entry point.** Startup reads it first. It is the
  "map of the vault + behavioral core" in one file.
- **Frontmatter is required** on cards and READMEs (see `frontmatter-contract.md`). A file
  with no frontmatter is undistinguished — the agent cannot tell what it is.
- **The types above are why each file exists** — not "dump everything in one folder".
- **Obsidian-compatible but not Obsidian-dependent.** `[[wikilinks]]`, `#tags`, and
  frontmatter work in Obsidian and in plain Markdown alike. No Obsidian → same files,
  just no graph view.

## Decision tree — "where does this go?"

When the agent (during closure or distillation) has a piece of information:

```
What did this session produce?
│
├─ Just edited text / did a one-off tactical task
│    → Nothing durable. The task's own file is enough.
│
├─ Made an architecture/policy choice
│    → append one entry to decisions.md
│
├─ Caught a repeating mistake or anti-pattern
│    → add a lesson to lessons.md (respect the budget)
│
├─ A durable person/project/concept appeared or changed
│    → create or update a card in people/ , projects/ , or cards/
│       (distillation; dedup first — see below)
│
├─ A single fresh fact, not yet a pattern
│    → append an episode to inbox.md
│
└─ Don't know where it goes
     → inbox.md (tended later by hygiene/closure)
```

## When NOT to write durable memory (anti-patterns)

These keep the vault from rotting. The generated skills must respect them.

- **Do not duplicate `profile.md`.** The profile is the single source for static facts;
  do not copy lines from it into decisions or cards.
- **Do not put tactical noise in `lessons.md`.** A lesson is a rule for years. "Today I
  forgot a flag" is not a lesson.
- **Do not let `lessons.md` exceed its budget.** When it grows past the budget, cut the
  oldest or promote a durable one into decisions.
- **Do not leave a card with no frontmatter.** No frontmatter = the agent cannot index or
  trust it.
- **Do not record a decision only in chat.** If a choice was made and never reached the
  vault, it is gone by next session.

## Deduplication (before creating a card)

Distillation and hygiene must avoid duplicate cards for the same entity:

1. **Exact match** — a card whose `id` (= filename without `.md`) equals the slug of the
   new entity already exists → update it, do not create a second.
2. **Similar-title heuristic** — a card whose `title` or `aliases` is a near-match (case-
   insensitive, ignoring punctuation, or a known alias) → surface it as a likely duplicate
   and ask/merge rather than silently creating a near-twin.

This is a string/alias heuristic, not semantic search — deliberately, to stay
infrastructure-free. Semantic dedup is out of scope for this package.
